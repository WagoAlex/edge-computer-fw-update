WAGO Edge Computer 0752-9xxx

Installing firmware through the edge WDA API

The container exposes WAGO's Device Access surface on an x86 edge and backs it with stock RAUC. Two payload routes share one state machine: the bundle baked into the image, and any signed .raucb you upload yourself.

https://192.168.2.17/wda host network, port 443, HTTP Basic, self-signed TLS

The state machine both routes drive

Every method call moves 0-0-firmwareupdate-status. Poll that parameter, not the HTTP status code: a failed method run still returns 201 and carries its verdict in the body.

0InactiveIdle. activate is the only useful call.
2PreparedStage directory ready. Upload slots can be reserved.
3Startedrauc install runs in the background; progress climbs 0 to 100.
4UnconfirmedInactive slot written and marked for next boot. Waiting for finish.
8FinishedFlashed and staged for the next boot. Nothing is confirmed yet. clear returns to Inactive.
7ErrorRead errorcause: 200 is a signature reject, 600 a failed install.

Two routes to a written slot

The difference is exactly one field. start with an empty UploadFiles installs the bundle inside the image; start with an upload id installs what you pushed. Everything before and after is identical.

Route A

The bundle in the image

No upload, no .wup handling. BUNDLE=/firmware/bundle.raucb is staged to the host-visible path and installed. Roughly 1.3 GB is copied first, so start returns long before anything is written. Available on the bundle-latest image; the 238 MB api-latest image ships without a bundle and answers this route with an error until one is mounted.

  1. 1

    Activate

    Creates STAGE_DIR and moves status to Prepared. A second activate while a run is live answers domainSpecificStatusCode: "90", which means already active, not broken.

    curl -sk -u admin:$PW -X POST \
  https://192.168.2.17/wda/methods/0-0-firmwareupdate-activate/runs?result-behavior=sync \
  -H 'Content-Type: application/vnd.api+json' \
  -d '{"data":{"type":"runs","attributes":{"inArgs":{
        "KeepCustomerApplication":{"value":false},
        "CustomKeyValuePairs":{"value":[]}}}}}'
  2. 2

    Start with no files

    An omitted or empty UploadFiles is the documented signal for the embedded bundle. There is no separate endpoint for it.

    curl -sk -u admin:$PW -X POST \
  .../0-0-firmwareupdate-start/runs?result-behavior=sync \
  -H 'Content-Type: application/vnd.api+json' \
  -d '{"data":{"type":"runs","attributes":{"inArgs":{
        "UploadFiles":{"value":[]}}}}}'

201 Created
{"data":{"type":"runs","attributes":{
   "outArgs":{},"executionStatus":"done"}}}
    If no bundle is baked in, the run comes back executionStatus: "error" with detail no embedded bundle and no UploadFiles given. Use route B.
  3. 3

    Poll status and progress

    Two plain parameter reads. Staging shows as 0 percent for a minute or two before RAUC starts reporting.

    watch -n6 'curl -sk -u admin:$PW \
  .../wda/parameters/0-0-firmwareupdate-progress \
  | python3 -c "import json,sys; \
    print(json.load(sys.stdin)[\"data\"][\"attributes\"][\"value\"])"'
Route B

Your own signed bundle

Reserve a slot, push the file in chunks, then name the slot in start. This is the path a stock WAGO client already speaks, so an unmodified fw_update.py drives it with no changes.

  1. 1

    Unpack the .wup first

    A .wup is a zip around package-info.xml and the real payload. The API takes the .raucb, never the wrapper.

    unzip -o firmware.wup -d /tmp/fwwork
ls /tmp/fwwork/*.raucb
  2. 2

    Activate, then reserve an upload id

    Same activate as route A. Then ask for one id per file name; each id becomes an empty file in STAGE_DIR on the shared bind mount.

    curl -sk -u admin:$PW -X POST \
  .../0-0-firmwareupdate-getuploadids/runs?result-behavior=sync \
  -H 'Content-Type: application/vnd.api+json' \
  -d '{"data":{"type":"runs","attributes":{"inArgs":{
        "FileNames":{"value":["firmware.raucb"]}}}}}'

201 Created
{"outArgs":{"UploadFiles":{"value":["9f2c41ab77e05d13"]}}}
    Calling this before activate returns domainSpecificStatusCode: "95" - not activated. Order is enforced.
  3. 3

    PATCH the bundle in byte ranges

    One multipart/byteranges part per request, placed by its Content-Range offset. 4 MB is the verified safe chunk size; each accepted chunk answers 204.

    PATCH /files/9f2c41ab77e05d13
Content-Type: multipart/byteranges; boundary=WAGOFW

--WAGOFW
Content-Type: application/octet-stream
Content-Range: bytes 0-3999999/1342177280

<4 MB of binary>
--WAGOFW--
    total=$(stat -c%s fw.raucb); off=0; n=4000000
while [ $off -lt $total ]; do
  end=$(( off + n - 1 )); [ $end -ge $total ] && end=$(( total - 1 ))
  printf -- '--WAGOFW\r\nContent-Type: application/octet-stream\r\n'\
'Content-Range: bytes %d-%d/%d\r\n\r\n' $off $end $total > /tmp/part
  dd if=fw.raucb bs=1 skip=$off count=$(( end - off + 1 )) >> /tmp/part 2>/dev/null
  printf '\r\n--WAGOFW--\r\n' >> /tmp/part
  curl -sk -u admin:$PW -X PATCH --data-binary @/tmp/part \
    -H 'Content-Type: multipart/byteranges; boundary=WAGOFW' \
    https://192.168.2.17/files/9f2c41ab77e05d13
  off=$(( end + 1 ))
done
    Chunk assembly strips exactly one trailing CRLF. A client that trims a byte set instead will silently corrupt any chunk ending in 0x0d, 0x0a or 0x2d.
  4. 4

    Start with the id

    The file is already on the host path RAUC reads, so nothing is copied. Verification happens here: the bundle signature is checked against the mounted host keyring.

    -d '{"data":{"type":"runs","attributes":{"inArgs":{
      "UploadFiles":{"value":["9f2c41ab77e05d13"]}}}}}'
    Self-signed bundles. A bundle built by make_edge_raucb.sh verifies against this edge's /etc/rauc/keyring.pem only. A genuine PFC or TP600 rejects it on the production signature check, and any bundle signed by a key this device does not trust lands in status 7 with errorcause 200.

Closing out, on either route

RAUC has written the inactive slot and set it for next boot. Nothing is permanent until the update is confirmed.

  1. 5

    Finish at status 4

    Moves to Finished (8): the bundle is written to the inactive slot and staged for the next boot. It does not mark anything good, because the device is still running the old slot and rauc status mark-good would confirm the slot being replaced. Read 0-0-firmwareupdate-pendingslot to see what is staged, then reboot (opt-in, Confirm=true) and confirm once it is running. Called in any other status it returns an error run with detail not finishable in status N.

    curl -sk -u admin:$PW -X POST \
  .../0-0-firmwareupdate-finish/runs?result-behavior=sync -d '{}'
  2. 6

    Clear, then reboot when you choose

    clear deletes the staged upload files and returns status to Inactive (0). The new slot boots on the next restart, which the API never triggers on its own.

    curl -sk -u admin:$PW -X POST \
  .../0-0-firmwareupdate-clear/runs?result-behavior=sync -d '{}'
  1. -

    Read the log ring at any point

    The last 200 update events live in memory and are also on stdout with timestamps, so docker logs is the audit trail that survives a restart.

    curl -sk -u admin:$PW -X POST \
  .../0-0-firmwareupdate-getlastlogentries/runs?result-behavior=sync \
  -d '{"data":{"type":"runs","attributes":{"inArgs":{
        "EntryCount":{"value":25}}}}}'

outArgs.Entries.value
[ "activate -> Prepared",
  "staging embedded bundle -> /docker/rauc-stage/embedded.raucb",
  "rauc install /docker/rauc-stage/embedded.raucb",
  "install done -> Unconfirmed (call finish)" ]
  2. -

    Abandon a run

    cancel drops straight back to Inactive with errorcause 101, AbortByUser. It does not stop a RAUC install already in flight.

    curl -sk -u admin:$PW -X POST \
  .../0-0-firmwareupdate-cancel/runs?result-behavior=sync -d '{}'

Building the bundle you upload

Route B needs a signed .raucb. There is no cross-build: the bundle is a capture of a running edge rootfs, so steps 1 to 7 run on the device itself, as root, under /docker. Building under /tmp is a tmpfs and will run the box out of memory. The finished script is build/make_edge_raucb.sh; the steps below are what it does and why each one is there.

Route B, upstream

From a running edge to a signed .wup

Roughly 25 minutes and about 3 GB of scratch space on the 33 GB work disk. The result is accepted by any device that trusts the same signing certificate, and by nothing else.

  1. 1
    On the edge, as root

    Provide the build tools

    mksquashfs is not in the base image and rauc bundle cannot run without it. Install it before the rootfs is tarred, so it is captured into the image and every device flashed from the result can build its own bundles.

    ssh root@192.168.2.17
apt-get update
apt-get install -y --no-install-recommends squashfs-tools
command -v rauc mksquashfs openssl
  2. 2
    On the edge, as root

    Create the signing key and certificate

    Self-signed, 4096 bit, ten years. The private key stays on this device and is excluded from the capture in step 5, so it never travels inside a bundle.

    openssl req -x509 -newkey rsa:4096 -nodes \
  -keyout /etc/rauc/key.pem -out /etc/rauc/cert.pem \
  -subj "/O=WAGO/CN=WAGO Edge Self-Signed" -days 3650
chmod 600 /etc/rauc/key.pem
  3. 3
    On the edge, as root

    Make the device trust that certificate

    RAUC verifies against the keyring named in system.conf. Register the certificate as the keyring before the capture, so the trust travels with the image and no device needs manual preparation later.

    cp /etc/rauc/cert.pem /etc/rauc/keyring.pem
grep -q '^\[keyring\]' /etc/rauc/system.conf \
  || printf '\n[keyring]\npath=/etc/rauc/keyring.pem\n' \
     >> /etc/rauc/system.conf
    This is the whole reason a self-signed bundle installs here and is rejected by a genuine PFC or TP600. Those check a production signature this line cannot forge.
  4. 4
    On the edge, as root

    Load loop and dm-verity at boot

    A verity bundle is mounted through a loop device. Without both modules, the install fails at Failed to open /dev/loop-control - and it fails on the target device, not here, so it has to be baked in now.

    mkdir -p /etc/modules-load.d
printf 'loop\ndm-verity\n' > /etc/modules-load.d/rauc.conf
  5. 5
    On the edge, as root

    Capture the live rootfs

    Volatile mounts, the work disk and the private key are excluded. Everything else, including the three files added above, goes into the payload.

    OUT=/docker/edge-build; mkdir -p $OUT/content
tar --numeric-owner --one-file-system \
    --exclude=./tmp/* --exclude=./proc/* --exclude=./sys/* \
    --exclude=./dev/* --exclude=./run/* --exclude=./mnt/* \
    --exclude=./media/* --exclude=./docker/* \
    --exclude=./lost+found --exclude=./etc/rauc/key.pem \
    -czf $OUT/content/rootfs.tar.gz -C / .
  6. 6
    On the edge, as root

    Write the manifest

    compatible must match /etc/rauc/system.conf character for character, or the install is refused on compatibility grounds before anything is written.

    cat > $OUT/content/manifest.raucm <<'EOF'
[update]
compatible=WAGO Edge Computer 752-9xxx
version=4.1.0

[bundle]
format=verity

[image.rootfs]
filename=rootfs.tar.gz
EOF
    Do not add sha256 or size lines. rauc bundle computes them itself and aborts with Unexpected digest if it finds them pre-filled.
  7. 7
    On the edge, as root

    Sign the bundle, then read it back

    rauc info against the keyring is the same check the API runs at start. If it passes here it will pass there; if it fails here, nothing else in this page will work.

    NAME=WAGO_OS0752-9xxx_Edge_FW5_V040100_IX05
rauc bundle --cert=/etc/rauc/cert.pem --key=/etc/rauc/key.pem \
  $OUT/content $OUT/$NAME.raucb

rauc info --keyring /etc/rauc/keyring.pem $OUT/$NAME.raucb
Compatible:  'WAGO Edge Computer 752-9xxx'
Version:     '4.1.0'
Verified inline signature by 'WAGO Edge Self-Signed'
  8. 8
    On the workstation

    Wrap it as a .wup

    Only needed for clients that resolve firmware from a catalog: a .wup is a zip of package-info.xml plus the bundle, with the XML stored first, exactly as WAGO ships them. The API itself always takes the bare .raucb.

    scp root@192.168.2.17:/docker/edge-build/$NAME.raucb bundles/
bash build/wrap_wup.sh          # writes bundles/$NAME.wup
unzip -l bundles/$NAME.wup
    The OrderNo in package-info.xml is the literal placeholder 0752-9xxx. A catalog client matches on that field, so set the real order number before pointing one at a live device.
